# Data model

This page is for contributors writing code that reads or writes the database, and for deployers who want to know what a deployment stores. The schema lives in `packages/core/migrations/`, applied in order by D1. The helpers that enforce the rules below live in `packages/core/src/data/` (`@gtm-agents/core/data`).

D1 is the source of truth. Blob storage, KV and the vector index are caches or archives that can be rebuilt from it.

## Conventions

- **Account key.** Account-level rows are keyed by `account_key`: the lowercased registrable domain of the company's website or work email (`acme.example`, `globex.co.uk`). `accountKey()` derives it from a URL, a single address or a domain. It returns `null` for personal mailboxes (including country variants such as `yahoo.fr`), shared hosts (code hosts, site builders, social networks, relay addresses) and anything that is not exactly one usable domain, so unrelated people are never grouped into one account. The caller skips rather than guesses. It does not bundle the full public suffix list: a country-code domain with a generic second label (`co`, `com`, `net`, `org` and similar) keys on three labels, and anything else on two.
- **Attributes.** Domain-specific fields go in the `attributes` JSON column of `contacts`, `accounts`, `candidates`, `deals` and a few others, never in new columns. A new column is only for data every deployment has. The column must hold valid JSON; the database refuses anything else.
- **Timestamps** are ISO 8601 UTC text (`2026-11-04T09:00:00.000Z`), so they compare correctly as strings. Every table has `created_at`, except the `memory_fts` search index.
- **Money** is integer cents (`value_cents`, `mrr_cents`) unless the column name says otherwise (`raised_usd` is whole dollars). Spend is micro-cents in the cost ledger.
- **Ids** are text, generated by the application, except `audit_log`, which numbers its rows.
- **Hashes** (`*_sha256`) are lowercase hex SHA-256; the database refuses anything else. Stored addresses are lowercase.
- **Emails on contacts** are stored normalized, with two hashes: `email_sha256` (the exact address) and `mailbox_sha256` (the address without a `+tag`). Suppression, erasure and the product bridge match on the hashes. `contactEmailFields()` produces all three, or `null` for an address that does not parse, in which case the contact is not stored.
- **Migrations** are numbered `NNNN_description.sql` and idempotent (`IF NOT EXISTS`). A migration that has been applied anywhere is never edited; changes go in a new, higher-numbered file. `npm run check:migrations` enforces the rules.

## Status enums

Each enum is defined once in `packages/core/src/data/enums.ts`, and the migrations' CHECK constraints list the same values. A test keeps the two in step. Do not invent parallel enums.

| Enum | Values | Rule |
|---|---|---|
| Contact warmth | `cold`, `contacted`, `warming`, `engaged`, `hot`, `customer`, then `churned`, `opted_out` | Climbs only. `opted_out` can be reached from anywhere, `churned` included, and `churned` only from `customer`; both are terminal. Write it with `advanceWarmth()`, a compare-and-set. A database trigger refuses any write that leaves a terminal state |
| Deal stage | `prospecting`, `contacted`, `engaged`, `demo_scheduled`, `trial`, `proposal`, `negotiation`, `closed_won`, `closed_lost` | Forward to any later stage, or to `closed_lost` from any open stage. Closed stages are terminal. Write it with `transitionDeal()`, which records `deal_stage_history` in the same batch |
| Candidate status | `raw`, `enriched`, `qualified`, `borderline`, `rejected`, `promoted`, `duplicate` | A candidate becomes a contact only through promotion |
| Draft status | `draft`, `pending_approval`, `approved`, `sent`, `rejected` | An approved draft must carry `approved_digest` ([SECURITY-MODEL.md](SECURITY-MODEL.md#approvals)). A database trigger returns an approved draft to `pending_approval` when its recipient, subject or body is edited |
| Lifecycle state | `sighted`, `qualified`, `parked`, `contacted`, `engaged`, `nurturing`, `opted_out` (before sign-up); `signed_up`, `stalled`, `activated`, `at_wall`, `paying`, `expanding`, `at_risk`, `churned` (in the product); `deleted` | One module writes it, by compare-and-set |
| Send path | `cold`, `sequence`, `reply`, `lifecycle` | Decides which send gates apply |
| Experiment metric | `positive_reply`, `meeting_booked`, `conversation_started`, `signed_up`, `activated`, `paid` | The only metrics an experiment can be pre-registered on. Each gets one implementation in the metrics module (milestone 5) |

Signal types, verification statuses, template kinds and taint levels come from the port interfaces and the template engine, and the schema uses the same lists.

## Erasure

A person is a mailbox: erasing `jane@acme.example` also erases `jane+news@acme.example`, and the reverse. `eraseContact(db, email, { source })` finds every contact stored under the mailbox and erases them in one batch, all or nothing:
1. **Tombstone.** It writes the exact and mailbox hashes to `erasure_tombstones`, so the person is never re-added or emailed. The suppression check reads it.
2. **Rows that hold the address without a contact link.** It deletes candidates and their evidence, drafts and deferred sends addressed to the person, inbound mail they sent, referrals naming them, operator chat messages that mention one of their stored addresses, and the cached verification results. Matching ignores case and surrounding spaces, and recognizes the `Name <address>` form.
3. **The contact row.** Deleting it lets foreign keys finish the job:
   - **Deleted with the contact (cascade):** per-contact state and anything holding their words. That covers tags, scores, fit, angles, evidence, lifecycle, drafts, the outreach log, inbound mail, meetings, calendar rows, feedback, signals and engagement.
   - **Kept, with `contact_id` cleared (set null):** ledgers used for measurement, such as `outreach_sends`, `funnel_events`, `events`, experiment assignments and deals. These hold no address, so reports stay honest after an erasure.

A test checks every foreign key to `contacts` against an explicit list of these decisions, and scans every text column after an erasure to confirm the address is gone.

`eraseByHash(db, emailSha256, { source })` handles an erasure that arrives as a hash only (the product's `user.deleted` event). When a contact holds that hash, the full erasure runs. Otherwise only the tombstone is written, and it blocks that exact address but not other subaddresses.

Erase only through these helpers. A trigger refuses to delete an opted-out contact unless a tombstone or suppression entry keeps the opt-out, so a stray delete cannot make the address sendable again. Another trigger refuses any write that moves warmth out of a terminal state. A bulk import that sets warmth must therefore skip opted-out and churned rows, or the whole statement fails.

Memory text is not linked to a contact, so the memory module removes it separately.

## Tables by group

### CRM (migration 0006)

| Table | Holds |
|---|---|
| `accounts` | One row per company, keyed by `account_key`: tier, segment, status, coverage |
| `contacts` | People: normalized email and hashes, account, title, warmth, verification and employment state |
| `contact_tags` | Free-form tags |
| `contact_lifecycle` | The customer lifecycle state, product ids, attribution and first-time timestamps |
| `contact_scores` | Targeting score and band |
| `contact_engagement` | Engagement score and trend |
| `contact_angles` | The reason to write now, from a dated signal |
| `contact_evidence` | Per-field evidence (email, title, employer) with conflicts held for a person |
| `contact_fit` | Keep, maybe or drop, and why |
| `account_contacts` | Who the system covers at an account, by persona |
| `account_context` | A pointer to an account's research context in blob storage |
| `graph_entities`, `graph_edges` | A small relationship graph |

### Pipeline (0007)

| Table | Holds |
|---|---|
| `deals`, `deal_stage_history` | Deals and every stage move |
| `deal_handoffs`, `deal_outcomes` | Briefs for the operator, and why deals were won or lost |
| `meetings`, `calendar_meetings` | Meeting notes; booked calls from calendar sync (event titles are never stored) |
| `proof_of_value_requests` | Product analysis runs for a prospect (sending the result is permanently human) |
| `subscriptions`, `billing_customers`, `mrr_snapshots` | Subscriptions, the billing provider's view, daily MRR |
| `referrals`, `ref_tokens` | Referral asks, and tokens that credit a sign-up to a touch |

### Outreach (0008)

| Table | Holds |
|---|---|
| `campaigns`, `campaign_contacts` | Campaigns and each contact's sequence state in them |
| `templates`, `copy_lines` | Uploaded templates with usage counts; operator-written lines templates assemble |
| `drafts` | Drafts and their approval digests |
| `outreach_log` | Every touch on any channel, for the contact's history |
| `outreach_sends` | The per-send ledger: the basis of every outreach metric and experiment |
| `outreach_sequence_runs`, `followups`, `followup_touches`, `manual_touches` | Sequences, follow-up decisions, multithreading and re-engagement, manual touches for the operator |
| `outreach_holdout` | The no-send control group |
| `deferred_sends`, `send_slot_schedules` | Sends held for the recipient's window or a cap |
| `email_verifications` | Verification results, keyed by address hash |
| `domain_delivery`, `seed_placements` | Delivery per recipient domain; seed inbox placement |
| `quality_checks` | Quality gate verdicts |
| `reply_assets`, `reply_qualifications`, `objections`, `persona_playbooks` | Links replies may offer, reply qualification, the objection library, per-persona playbooks |

Open and click counts are deliberately absent, per contact or in aggregate: mail is plain text with no tracking pixels or click tracking, and replies are the metric. Booked meetings are detected by calendar sync, not by tracking clicks on the booking link. `suppression` (migration 0005) belongs to this group too.

### Experiments (0009)

`experiments`, `experiment_assignments`, `experiment_proposals`, `subject_tests`, `subject_variants`, `subject_assignments`, `knob_proposals`, `qualification_weights`. An experiment's metric is one of `EXPERIMENT_METRICS`. Counts on these tables are caches; the send ledger is the source of truth.

### Discovery (0010)

`discovery_queries`, `candidates`, `icp_snapshots`, `monitor_items`, `signal_events`, and account-level research keyed by `account_key`: `account_fit`, `account_facts`, `account_hiring_roles`, `account_job_boards`, `account_board_checks`, `domain_resolutions`, `resource_claims`, `title_fit_reviews`.

### Events (0011)

`inbound_emails`, `events` (the event spine, each row with a taint level), `funnel_events`, `engagement_events`, `lifecycle_transitions`, `erasure_tombstones`.

### Agent operations (0012)

`audit_log`, `provider_runs`, `delegation_tasks`, `tasks`, `benchmark_runs`, `fitness_scores`, `evolution_runs`, `autonomy_events`, `learnings_proposals`, `mcp_servers`, `goals`, `plans`, and `memory_fts`, a full-text index over memory text. Virtual tables are not included in `wrangler d1 export`; the index is rebuilt from memory. With `event_effects` (0002), `execution_runs` (0003) and `cost_events` (0004), they record what ran, what it cost and what was learned.

### Ship loop and link intake (0013)

`feedback_items`, `themes`, `ship_tasks`, `link_items`, used by the optional modules. Feedback text is full taint.

### Chat, delivery and outreach (0014 to 0016)

- `chat_sessions` and `chat_messages` (0014): operator chat history and the session's taint, which persists until `/clean`.
- `deferred_send_items` (0015): the items waiting in the deferred queue, with a deduplication key that is released when an item leaves the queue.
- `approval_manifests` (0016): the manifest each manual cold batch is released against.

## What is not in core

Tables that only make sense for one market belong in a domain pack under `examples/packs/`, not in core. Examples: an investor's portfolio companies and check sizes, or a domain knowledge wiki. A pack adds its own migrations, and keeps per-record fields in `attributes`.
